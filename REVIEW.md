# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `list_employees` / `skip = page * page_size` | Off-by-one pagination: page 1 skips 20 records, page 2 skips 40, etc. Page 1 is always empty. | `GET /employees?page=1` returns no items even with 6 employees in the DB. | Changed to `(page - 1) * page_size`. |
| 2 | `list_employees` / `count_documents({})` | The total count ignores the `department` filter, so a filtered list reports the wrong total. | `GET /employees?department=Engineering` returns `total: 6` (all employees) instead of `total: 2`. | Changed to `count_documents(q)` where `q` is the same filter used in `find`. |
| 3 | `health` / entire function | No actual DB ping — always returns 200 even when MongoDB is down. The runner relies on this endpoint to know the app is ready. | Stop mongod, hit `GET /health` — still gets 200. | Added `db.command("ping")` inside a try/except; raises 503 on failure. |
| 4 | `create_employee` / check-then-insert | Race condition: two concurrent identical `emp_code` requests both pass the `find_one` check, then both insert, creating a duplicate. Also, no unique index enforced the constraint in the DB. | Send two simultaneous POST /employees with the same emp_code — both return 201 (only one should). | Removed the pre-check; inserted directly and caught `DuplicateKeyError`. Created a unique index on `emp_code` at startup. |
| 5 | `create_employee` / `datetime.now()` | Naive datetime (no timezone). PyMongo stores it but it represents local machine time, not UTC. Comparisons with UTC-aware datetimes from other operations will fail or give wrong results. | On a machine in IST, `created_at` is stored as IST time but treated as UTC in responses — off by 5.5 hours. | Changed to `datetime.now(tz=timezone.utc)`. Also set `tz_aware=True` on `MongoClient` so PyMongo returns aware datetimes. |
| 6 | `create_employee` / response shape | Returns the raw dict with `_id` still present (after `pop` it's gone) but `created_at` is a Python `datetime` object, not epoch milliseconds. The OpenAPI spec says `created_at` must be an integer epoch-ms. | `POST /employees` response contains `"created_at": "2026-10-12T..."` (string from datetime) instead of an integer. | Added `serialize_employee()` which converts `created_at` to `dt_to_ms()` and removes `_id`. |
| 7 | `punch_in` / `datetime.fromtimestamp(body.punched_at / 1000)` | `fromtimestamp` uses **local time** (IST on this machine), not UTC. The datetime stored in MongoDB is wrong. On a UTC-only server the punch_in time would be right but IST offset would be missing, causing naive-vs-aware comparison errors. | Punch in with `punched_at=1783310280000` (09:28 IST). The stored `punch_in` is 5.5 hours ahead of the correct UTC value. | Replaced with `datetime.fromtimestamp(ms // 1000, tz=timezone.utc)` — always UTC-aware. |
| 8 | `punch_in` / no 404 for unknown employee | If `emp_code` does not exist, `find_one` returns `None`. The next line `emp["shift_start"]` crashes with `TypeError: 'NoneType' object is not subscriptable` — a 500, not the required 404. | `POST /attendance/punch-in` with `{"emp_code": "EMP9999"}` — server returns 500. | Added `if not emp: raise HTTPException(404, ...)` immediately after the find. |
| 9 | `punch_in` / attendance date from local time | `ts.date()` called on a naive local-time datetime. On IST the date changes 5.5 hours before UTC midnight, so a punch at 00:01 IST is filed under the next UTC date. | Punch in at 00:05 IST (18:35 UTC previous day) — `date` stored as the next day. | Replaced with `attendance_date_ist()` which converts punch_in to IST first, then applies overnight-shift logic. |
| 10 | `compute_late_minutes` / wrong TZ for shift start | `punch_in.replace(hour=h, minute=m)` keeps whatever tzinfo is on `punch_in`. If punch_in is naive local time, shift_start ends up as naive local time. The subtraction `punch_in - start` then compares two naive locals — accidentally correct on the same machine, but wrong if stored UTC is used. Also, the function uses `punch_in.replace(...)` which pins the shift-start to the SAME instant as punch_in (correct date), so that part works, but only by luck when punch_in is local time. | On a UTC server with punch_in stored as UTC, the shift-start would be computed in UTC, making late calculations wrong by 5.5 h. | Rewrote `compute_late_minutes` to take `date_str` and reconstruct shift-start as an IST-aware datetime, then compare with UTC-aware punch_in. |
| 11 | `compute_late_minutes` / grace-period check | `minutes > 10` is correct for the threshold, but the return value `minutes` (minutes since shift_start) is correct per R2. **Not a bug** — but confusingly named. Left as is, renamed variable to `diff_min` for clarity. | — | No change to logic; renamed variable for readability. |
| 12 | `compute_overtime` / no 30-minute minimum | The function returns any positive difference without checking the 30-minute rule (R3). An employee who leaves 5 minutes late would get 5 overtime minutes. | Punch out 10 min after shift_end — overtime_minutes should be 0, but starter returns 10. | Added `return diff_min if diff_min >= 30 else 0`. |
| 13 | `compute_overtime` / wrong date for overnight shifts | For overnight shifts (shift_end <= shift_start), `shift_end` occurs on the NEXT calendar day. The starter always uses `date_str` (the attendance date), placing shift_end on the wrong day and making the overtime calculation up to 24 hours off. | For EMP0005 (22:00–06:00 shift), punch out at 06:40 IST the next day — starter computes a huge negative or huge positive overtime. | Added a check: if `shift_end <= shift_start`, add one day to `shift_date` before constructing `shift_end_ist`. |
| 14 | `list_attendance` / loads entire collection into Python | `list(db.attendance_logs.find(q))` fetches every matching document into RAM, then sorts in Python. On 100,000 records this OOMs or is extremely slow. | With 100k records, `GET /attendance` takes many seconds and uses gigabytes of RAM. | Used `.sort([...]).skip(skip).limit(page_size)` on the cursor, backed by a compound index; never loads more than `page_size` documents. |
| 15 | `list_attendance` / wrong total | `total = len(docs)` — this counts only the documents returned after loading all into memory, but it would still be wrong once paginated. Actually it counts the whole filter result before slicing, which happens to be correct total, but the approach doesn't scale. The real bug is combining load-all with pagination. | Performance issue, not logical bug for small datasets. | Used `count_documents(q)` for total; cursor for data. |
| 16 | `list_attendance` / exposes `_id` in response | `d["id"] = str(d.pop("_id"))` — renames `_id` to `id` and puts it in the response. The spec says `_id` is never returned; the `AttendanceRecord` schema has no `id` field. | `GET /attendance` response contains `"id": "..."` which the grader's schema check will flag. | Removed the `_id` mapping; added `{"_id": 0}` projection so it's never fetched, and `serialize_record()` pops it as a safety net. |
| 17 | `punch_in` / response contains `"id"` | Same as #16 — `doc["id"] = str(res.inserted_id)` returns an `id` field. | `POST /attendance/punch-in` response contains an unexpected `id` field. | Removed that line; `serialize_record()` handles the response shape. |

## Things examined and decided NOT to be defects

- The `IST = timezone(...)` constant — correct offset, not a bug.
- `body.model_dump()` in `create_employee` — correct Pydantic v2 API.
- Using `find_one` with `sort` in the starter's punch-in — it was already the right pattern conceptually, just wrong on TZ.
- `Optional[int] = None` for `punched_at` — correct default.
